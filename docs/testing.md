# テスト方針

RaiseTimeLineにおけるテストの目的と、レイヤーごとのテスト方針をまとめたドキュメント。

## 1. なぜテストを書くのか

本プロジェクトは学習目的の個人開発だが、実務で求められる開発フローを体験するため、以下を目的にテストを整備している。

- **リグレッション防止**: 機能追加・リファクタ時に既存機能を壊していないことを機械的に保証する。手動確認だけでは画面ごとの組み合わせを毎回網羅できないため、特に「所有権チェック」「認証・認可」まわりのように壊れても気づきにくい箇所を重点的にカバーする。
- **設計の検証**: テストが書きにくいコードは大抵、責務が分離できていないサインである。Service層のユニットテストを書くこと自体が、Controller/Service/Mapperの責務分割が妥当かを検証する手段になっている。
- **仕様のドキュメント化**: テストケース名・アサーションが「この機能は何を保証すべきか」を示す生きた仕様書として機能する。

## 2. レイヤーごとの方針

| レイヤー | 対象 | 使用技術 | 主な観点 |
|---|---|---|---|
| Mapper | `backend/src/test/java/.../mapper/*MapperTest.java` | JUnit 5 + H2（インメモリDB） | XMLマッパーに書いたSQLが意図通りの結果を返すか（実DBに近い形で検証） |
| Service | `backend/src/test/java/.../service/*ServiceTest.java` | JUnit 5 + Mockito | ビジネスロジック（所有権チェック、バリデーション、例外送出など）の単体検証 |
| Controller | `backend/src/test/java/.../controller/*ControllerTest.java` | JUnit 5 + standalone MockMvc | リクエスト/レスポンスのマッピング、認証済みユーザーの扱い、HTTPステータス |
| フロントエンド（ユニット） | `frontend/test/unit/*.test.js` | Vitest | API呼び出しロジック・データ整形などのロジック単体 |
| フロントエンド（コンポーネント） | `frontend/test/component/*.test.js` | Vitest + jsdom | DOM操作・イベントハンドリングを含むUIコンポーネントの振る舞い |

テストケースは実装前にブラックボックス（仕様から見た正常系・異常系）とホワイトボックス（分岐網羅）の両観点で洗い出してから着手する方針としている。

## 3. E2Eテスト（任意実行）

主要な画面遷移・ユーザー操作（認証、投稿CRUD、いいね/コメント、フォロー、所有権による表示制御など）に対する[Playwright](https://playwright.dev/)ベースのE2Eテストを`e2e/`配下に整備している。

- 目的: 画面をまたぐ回帰、特に「投稿者本人以外によるいいね/コメント」のような複数ユーザーが絡むシナリオを機械的に検証すること。以前はChrome DevTools MCPを使った手動確認で代替していたが、毎回の網羅が難しいためE2Eテストとして自動化した。
- テストケースはシナリオ（黒箱）観点で、画面遷移図・機能一覧をベースに正常系・主要な異常系・認可/所有権を洗い出してから着手する方針。
- 実行タイミング: CIには組み込まない。`perf-test/`と同様、大きめのリファクタや画面変更時など、開発者が任意のタイミングで手動実行する。
- 実行方法: [e2e/README.md](../e2e/README.md) を参照。`npx playwright test tests/scenarios`で実行する。
- スコープ外: 新着投稿ポーリング通知のE2E化（間隔待ちが絡みテストが不安定になりやすいため）、CI自動実行。

### ブラウザパフォーマンス計測

`e2e/tests/perf/`に、Navigation Timing APIや操作前後のタイミング差分を使った**実ブラウザでの体感速度**の計測を追加している（`perf-test/`のAPIレイヤー負荷テストとは別レイヤー）。ログイン→タイムライン遷移、投稿送信→DOM反映などの主要導線を対象とし、結果はJSON出力とターミナル表示で確認する。こちらもCIには組み込まず、明らかな性能劣化への気づきを目的とした任意実行に留める。

## 4. パフォーマンステスト（任意実行）

主要API（タイムライン取得・いいねトグル・投稿作成・ログイン）に対するk6ベースの負荷テストを `perf-test/` 配下に整備している。

- 目的: 明らかな性能劣化やN+1・ロック競合などの作り込みバグに気づくこと。継続的な性能監視やキャパシティプランニングは対象外。
- 実行タイミング: CIには組み込まない。大きめのリファクタやクエリ・インデックス変更時など、開発者が任意のタイミングで手動実行する。
- 実行方法: [perf-test/README.md](../perf-test/README.md) を参照。`./perf-test/run.sh <scenario>` で実行する。
- スコープ外: 常設監視基盤（Grafana/InfluxDB等）、本番相当スケールでのキャパシティ計画、CI自動実行。
