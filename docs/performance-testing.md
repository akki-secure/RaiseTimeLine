# パフォーマンステスト方針

RaiseTimeLineにおけるパフォーマンステストの目的・対象・実行方法をまとめたドキュメント。[docs/testing.md](testing.md)で定義している単体/結合テストとは異なり、**機能追加のたびに自動実行するものではなく、任意のタイミングで手動実行する**。

## 1. なぜ自動実行にしないのか

- 単体/結合テストはリグレッション検知が目的で、コードの変更差分に対して常に高速に結果を返す必要がある。
- パフォーマンステストは実行に時間がかかり（同時接続シナリオ・ウォームアップ時間を含む）、CI相当のたびに走らせるとフィードバックループが遅くなる。
- 学習目的のプロジェクトであり負荷特性を都度追う必要性は低いため、「気になったタイミングで測る」運用の方が実態に合っている。

そのため `perf-test/` 配下にk6スクリプトとして切り出し、`./perf-test/run.sh <scenario>` で手動起動する形にしている。詳細な実行方法は[perf-test/README.md](../perf-test/README.md)を参照。

## 2. 対象範囲

バックエンドAPI（Spring Boot 3.4.5 + Java 21 + MyBatis + PostgreSQL 16）を対象とする。フロントエンドはビルド不要の静的HTML/JS/CSSであり、ブラウザ描画性能はスコープ外（必要になった場合はChrome DevTools MCPのPerformance機能で別途計測する）。

## 3. 使用ツール

| 用途 | ツール | 理由 |
|---|---|---|
| 負荷生成 | [k6](https://k6.io/) | シナリオをJavaScriptで記述でき、Gitでバージョン管理しやすい。JMeterのようなGUI専用ツールよりコードレビューに乗せやすい |
| サーバー内部指標 | Spring Boot Actuator + Micrometer | レスポンスタイムだけでなく、DBコネクションプール（HikariCP）使用率・JVMヒープ/GC時間などボトルネックの切り分けに必要な指標を取得する |
| 対象DB | Docker上のPostgreSQL 16（本番相当） | H2はMyBatisのSQL検証用のインメモリDBであり、性能特性が異なるため負荷試験には使わない |

Actuatorは現時点で`backend/build.gradle`に未導入。パフォーマンステストを実施する回だけ一時的に依存を追加する運用とし、常時本番稼働に組み込むかは別途判断する。

## 4. 対象シナリオ

`perf-test/scripts/scenarios/`配下に実装済み。

| # | シナリオ | 対象API | 主な観点 |
|---|---|---|---|
| 1 | 同時ログイン | `POST /api/auth/login` | JWT発行コスト、BCrypt検証のCPU負荷 |
| 2 | タイムライン取得 | `GET /api/posts`（タイムライン系） | ページング時のN+1有無、`PostMapper.xml`のJOIN設計が効いているか |
| 3 | 投稿作成 | `POST /api/posts` | DB書き込み負荷。画像添付時はS3アップロードを含めた計測を別枠で行う |
| 4 | いいね（同時実行） | `POST /api/posts/{id}/likes` | 同一投稿への同時いいねによるロック競合・所有権チェックの排他制御コスト |

フォロー一覧取得（`GET /api/users/{username}/follows`）は今後の課題として未実装。

## 5. 計測指標としきい値の考え方

- レスポンスタイム: p50 / p95 / p99
- スループット: req/s
- エラー率: 5xx・タイムアウトの割合
- サーバー内部: DBコネクションプール使用率、JVM GCによる停止時間

学習目的のプロジェクトでありトラフィック規模の想定がないため、明確なSLA（「p95が200ms以内」等）は現時点で定めない。まずは計測して現状値を把握し、実装変更（インデックス追加・N+1解消など）の効果をBefore/Afterで比較する使い方を基本とする。

## 6. 実行手順（概要）

1. `docker compose up -d --wait` でPostgreSQLを起動（本番相当のデータ量に近づけるため、必要に応じてテストデータを投入する）
2. バックエンドを起動（`docs/logging-operations.md`のログ設計に沿って構造化ログが出力される状態で実施し、ログからもボトルネックを追えるようにする）
3. k6シナリオを実行し、結果（p50/p95/p99・エラー率）を記録する
4. 実行中に30分を超えている場合はフリーズの可能性があるため、処理を止めてユーザーに確認する

## 7. スコープ外

- CI上での自動実行（前述の理由により対象外）
- フロントエンドのブラウザ描画性能測定（別途Chrome DevTools MCPで対応）
- 本番相当の大規模データでのロングランテスト（学習目的のため対象外）
